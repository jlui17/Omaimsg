omaimsg

how it works

Three programs, two machines, one straight line. Your Linux box runs a dumb UI and a smart daemon. A Mac runs BlueBubbles, which is our whole view of Apple. This page covers the parts that stay the same from release to release: who does what, how they talk, and where the data sits. Things that change on a whim, like keybindings and page sizes, are left out on purpose.

How it works, in fourteen pieces

Each one is short enough to check against a diff. Open one to see why we do it that way, and what it looks like when someone gets it wrong.

1 The panel just draws things. It never touches the network, never saves anything, and never works out what the data means.

This is what lets the UI reload while you use it, run a copy on every monitor, and get rewritten without anyone touching the backend. It also means two monitors can't show different numbers, because there is only one place an answer can come from.

The only things the plugin reaches out to are the Unix socket, and two Process blocks whose whole job is to start the daemon when the socket is dead.

Something's off if you see XMLHttpRequest or any HTTP in a .qml file · QML reading config.json · a third Process doing real work instead of starting the daemon · QML writing a settings or cache file · the panel sorting or filtering the chat list itself, instead of drawing the order it was handed.
2 The daemon does all the talking and holds all the truth. One daemon, any number of panels.

Unread counts, chat order, contact names, how fresh the cache is: all worked out once, then handed to whoever asks. Two panels disagreeing isn't something we have to remember to avoid. It just can't happen.

If the daemon isn't running, the plugin starts it and reconnects. The daemon itself never starts a client, never addresses one in particular, and never depends on one being there.

Something's off if you see state stored per client · a counter that belongs to one connection · the daemon assuming there is exactly one panel · any calculation that would give two panels different answers.
3 Only one file knows what BlueBubbles' data looks like: daemon/lib/bluebubbles.js.

That file is the whole adapter. It holds the REST client, the websocket session, contact lookups, and the translation into our own Chat and Message objects. Everything past it is written in our words, so when BlueBubbles changes its API, we change one file.

Nice side effect: you can check this with grep, which is what makes it a real rule instead of a good intention.

Something's off if you see isFromMe, dateCreated, handle, or a {status, message, data} wrapper showing up in index.js, store.js, bus.js, or any .qml file.
4 The socket protocol is written down in docs/daemon-protocol.md, and the doc changes in the same commit as the code.

The wire is simple: one JSON object per line, and a t field saying what kind of frame it is. But the two programs ship separately. The plugin arrives as a git clone, the daemon as a committed bundle, and they can easily be different ages. The doc is the only thing keeping them honest.

New frame types will get added over time. That's fine. The shape of the wire, and this rule, don't move.

Something's off if you see a new case in the daemon's frame router, or a new field on a Chat or Message, with no matching change to the protocol doc · a frame that spans more than one line · a frame with no t.
5 Ask a question, get an answer. Change something shared, and everybody hears about it.

Pinning a chat is the clearest example. You send pin, and instead of replying just to you, the daemon sends a fresh chats frame to every panel. Nobody else goes stale, and nobody else had to ask.

New messages, connection changes, unread changes: all pushed. Nothing polls.

Something's off if you see sendTo(client, ...) after something changed shared state · a panel on a timer, asking for something the daemon could have just told it.
6 Answer from the cache right away, then check with the server. Only send a second answer if it's actually different.

This is how both the chat list and threads work. The panel opens instantly on what we already had, then corrects itself, but only when there's something to correct. So one request can produce two replies, or just one.

The failure half matters more than the happy half. When the re-check fails, the answer we already gave stands, and we don't send an error. A BlueBubbles outage reaches you through the state frame and nowhere else. That way a flaky connection never blanks your screen or throws error toasts at you.

Something's off if you see an error frame coming out of a re-check · a second frame sent every time regardless · a spinner that waits on the network instead of drawing the cached answer · cached data getting cleared because a fetch failed.
7 A messages frame is the whole thread, not new bits to tack on.

This follows straight from the one above. Since a request can come back twice, and the second one is a correction, the panel can't append. It swaps the thread out whole, which also means it throws away any older pages loaded behind it (14).

Exactly two frames add rather than replace, and both say so in their name: a message push puts one message on the end, and an olderMessages reply puts a page on the front (14). Everything else replaces.

Something's off if you see the panel appending or merging a messages frame into what it already had · the panel assuming one reply per request · the daemon sending a partial page as a messages frame · a third frame type that adds instead of replacing.
8 Your message shows up the moment you press Enter, and you only ever see it once.

The composer draws your message straight away and lets the round trip catch up. Two things make that safe. The ack comes back carrying the tempId you made up, plus the real message id. And when the server echoes your own send back over the websocket, that echo carries your tempId too, so the row you already drew gets upgraded instead of duplicated.

The server sends that echo more than once for a single message. Deduplicating is the daemon's job, so no panel has to think about it.

Something's off if you see the panel waiting for ack before drawing · an echo matched on text or timestamp instead of tempId · the already-seen check removed · your own sends going back to you but not to the other panels.
9 The daemon decides the order of the chat list. Not BlueBubbles, and not the panel.

We tried letting the server sort. Its sorting and paging quietly drop merged chats, which we confirmed against a real server. So the daemon pulls the full list, every page of it, and sorts here: pinned chats first, then most recent message, then chats we know nothing about, at the end of their group.

Pins live on our side too, because Apple keeps phone pins somewhere the server can't see.

Something's off if you see a sort handed to the server and the result trusted · only the first page being fetched · the panel re-sorting what it was given · a filter that only searches the chats already loaded instead of asking for all of them.
10 Once we know something, we keep it. A thinner answer never wipes out a better one.

The server sometimes leaves out a chat's last-message preview, even when we ask for it. If we wrote that straight through, previews would flicker to blank and back. So anything we know stays until something better replaces it, and a field only reads empty when we have genuinely never seen anything for it.

Treat this as the general rule for merging anything from a source you can't trust, not a one-off patch on one field.

Something's off if you see a fetched object assigned over a cached one wholesale · a preview or a count that can go from known back to blank · "field missing" being read as "field is now empty".
11 The Mac decides what's read. That only ever flows toward us.

At startup we ask the server for a starting point, then track from there: up one on each incoming message, cleared when you read the chat here, or when the server tells us you read it on your phone. None of it is saved on Linux, because we work it out again on every start anyway.

Reading a chat in omaimsg does not mark it read on Apple's side. That's how the boundary works, not a gap to paper over locally.

Something's off if you see unread counts written to disk · a local counter that can drift away from what the Mac says · unread worked out from whatever the panel happened to show.
12 We never copy your messages onto Linux. Only three things get written to disk.

Your config, your pins, and cached image files. Everything else, the chat list, threads, unread counts, lives in memory and dies with the daemon. That's deliberate. The Mac is the one source of truth, and a second copy is just a second thing that can be wrong.

Every path we write lives in daemon/lib/paths.js, so the complete list of what we touch is one short file.

Something's off if you see a new SQLite file or JSON store for messages · a path built somewhere other than paths.js · a hardcoded ~/.config or /tmp instead of an XDG variable with a fallback.
13 Change the daemon, rebuild the bundle, run the smoke test.

When someone installs with omarchy plugin add, they get a plain git clone. No build step, no node_modules. So the committed bundle is the daemon people run. Source without a rebuilt bundle means your fix doesn't exist for anyone who installed the normal way.

node test/smoke.js starts a fake BlueBubbles server and the daemon, then pushes every protocol frame through a real Unix socket. It's the check for any daemon or protocol change, and it has to pass against the bundle too.

Something's off if you see a diff touching daemon/ without touching daemon/dist/omaimsg-daemon.cjs · a new frame type with nothing in the smoke test · a new assertion nobody watched fail first.
14 A thread loads a page at a time, backwards. The daemon decides how big a page is; the panel asks for the one before what it holds.

The panel used to name the number and the daemon kept a matching one next to it, the two held in step by a comment. Now there is a single number, in the daemon's config, and it is both the page we serve and the tail we keep in memory. They can't drift apart because they aren't two things.

Reaching the top of a thread asks for the page before it, and that reply is prepended (7). It lands at the far end of the list, above what you're reading, so nothing on screen moves.

The cursor is a timestamp, and the server's cut on it is inclusive: the message you asked from comes back with every page. That is deliberate. The server has no exclusive form, and shaving a millisecond off to fake one would drop any message sharing that millisecond, out of that page and out of every later one, because cursors only ever move backwards. So pages overlap by design, the panel drops what it already has by id, and "nothing older left" means nothing strictly older came back, not that the page was empty.

Something's off if you see a page size in manifest.json or in a .qml file · a cache limit and a page size kept as two numbers · a cursor adjusted by one to fake an exclusive cut · a last page discarded instead of merged because it said there was nothing older · the panel scrolling itself back into place after a page lands.

What the two sides say to each other

The words on the wire, and which file owns what.

The two objects that go over the socket

Our words, not Apple's. Fields get added over time, but the shape and who makes them don't move. Only daemon/lib/bluebubbles.js builds these; everyone else just reads them (3).

Chat    { guid, name, isGroup, pinned, lastMessage: { text, ts, fromMe }, unread }

Message { guid, text, ts, fromMe, sender, attachments?, tempId? }

ts        always unix milliseconds
sender    a real display name, "" when it's from you
tempId    only on the echo of your own send      (8)
lastMessage  null only if we have never seen one  (10)
Which file does what

One job each, tagged with the pieces above that it enforces. If a change doesn't fit in any of these boxes, that's worth a second look.

BarWidget.qml   sits in the bar, draws the badge, handles IPC
Client.qml      owns the socket: connect, reconnect, start the daemon
Panel.qml       the popup: chat list, thread, composer

daemon/index.js       routes frames. the only place frame types are named
daemon/lib/bus.js     the socket, the list of panels, fan-out       (5)
daemon/lib/store.js   what we know: chats, threads, unread      (9 10 12 14)
daemon/lib/bluebubbles.js  everything Apple-facing                  (3)
daemon/lib/contacts.js     turns an address into a name
daemon/lib/pins.js         the one thing we keep between runs
daemon/lib/paths.js        every path we write, in one file          (12)

Following one thing all the way through

The same pieces, in motion.

A message comes in  everyone hears about it
1
BlueBubbles
sends it down the websocket.
2
daemon
throws it away if we already forwarded that id (8), looks up the sender's name, adds one to unread (11), updates the chat preview (10) and the list order (9).
3
daemon
sends one message frame to every panel, with the message, the updated chat row, and the new total (5).
4
plugin
adds the row and updates the badge. One of only two frames that add rather than replace (7).
You send a message  draw first, confirm later
1
plugin
draws the row immediately under a made-up tempId, sends send (8).
2
daemon
posts it to the server with that id attached.
3
BlueBubbles
hands it to Apple, replies with the real message id.
4
daemon
sends back ack, carrying both ids.
5
BlueBubbles
also echoes the message on the websocket, more than once, under one id.
6
daemon
forwards it once, to all panels, still carrying the tempId.
7
plugin
upgrades the row it already drew. No duplicate, no flicker.
You open the panel  cache now, truth in a moment
1
plugin
connects, says hello, then asks for chats.
2
daemon
replies with state and the cached chat list, right away (6).
3
daemon
re-fetches the full list, sorts it here (9), and sends a second chats frame only if it differs. If that fetch fails, the first answer stands and you never hear about it (6).
4
plugin
you open a chat. Same two steps, and each reply replaces the thread (7).
5
plugin
asks for each image by id; the daemon hands back a file path, from the cache or freshly downloaded (12).
You scroll to the top of a thread  the page before this one
1
plugin
the thread is drawn newest-at-the-bottom, so the top of it is the oldest message on hand. Reaching it sends olderMessages carrying that message's timestamp (14).
2
daemon
goes straight to the server. There is nothing to answer from memory: what we keep is the newest page, and this asks for what sits behind it (14).
3
daemon
replies once, with a page oldest-first, plus whether anything older is left. Only one reply, never two: there was no cached answer to correct (6).
4
plugin
drops by id whatever it already had, including the message it asked from, and puts the rest on the front (7). The new rows land above what you're reading, so your place doesn't move.
5
plugin
once the answer says nothing older is left, it stops asking. Leaving the chat and coming back reloads the tail, and it can page again from there.

Left out on purpose: keybindings, page sizes and cache limits, which send method is the default, what's built so far, and anything measured against one server on one day. Those change without the architecture changing, so they live where they can: README.md for scope and keys, manifest.json for defaults, docs/daemon-protocol.md for the live frame list and every field, docs/research/ for why BlueBubbles and why this plugin shape.
